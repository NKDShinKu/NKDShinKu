很多开发者觉得 SEO 是玄学——堆关键词、买外链、研究算法漏洞。但对一个个人博客来说，SEO 的本质朴素得多：**让爬虫看得懂你的站，让分享平台愿意展示你的内容，让 AI 敢于引用你的文字**。这三件事没有一件是玄学，全部是可以逐项打勾的基建工程。

这篇以我自己的 Next.js 静态导出博客为例，把 SEO 讲完整：先说搜索引擎怎么看待你的网站，再逐项过一遍我做了什么、为什么这么做，最后汇总成一份可以直接抄走的自查清单。

> **要点速览**
>
> - SEO 的地基只有三件事：每页独立的元信息、完整的站点地图、清晰的内容结构——静态站在这三件事上有天然优势
> - 结构化数据（JSON-LD）让机器「看懂」内容而非仅仅「读到」文字；但 Google 已于 2026 年 5 月全面退役 FAQ 富结果，别把宝押在单一富结果上
> - 社交分享卡（Open Graph）决定链接在聊天软件和社交平台里的样子，直接影响点击率
> - 性能即 SEO：Core Web Vitals 是正式排名信号，静态导出的架构在这里躺赢
> - AI 时代的入口正在形成：llms.txt 是一份写给大模型看的「站点说明书」，成本低到值得赌

## 先搞懂：搜索引擎怎么「看」一个网站

搜索引擎与你的站点之间只发生三件事：

1. **抓取（Crawl）**：爬虫顺着链接和 sitemap 访问你的页面，拿到 HTML；
2. **收录（Index）**：解析 HTML，理解页面主题，存进索引库；
3. **排名（Rank）**：用户搜索时，按相关性和质量从索引里挑出结果排序。

SEO 要做的，就是让这三步都不卡壳。抓取阶段需要爬虫能找到所有页面（sitemap、内链）、不被 robots.txt 误伤；收录阶段需要机器能读懂页面结构（语义化 HTML、元信息、结构化数据）；排名阶段拼的是内容质量与体验（这就是「内容为王」的真正含义——技术基建只是让好内容不被埋没，替代不了内容本身）。

静态站在这个模型里有天然优势：HTML 在构建期就渲染完毕，爬虫拿到的就是完整内容，不存在「客户端渲染导致爬虫看到白屏」的经典问题；页面秒开、托管稳定，体验信号全部拉满。**静态博客做 SEO，起点就比很多动态站高**。

还有一个诚实的提醒：Google 的官方口径一直是「内容质量与有用性」才是排名核心（官方称谓叫 E-E-A-T：经验、专业、权威、可信）。技术 SEO 做的是「不丢分」，分数的上限由内容决定。

## 地基：每页独立的元信息

搜索引擎判断一个页面「讲什么」，第一眼看的还是传统元信息。我在 Next.js 的 Metadata API 里做了这几件事：

- **标题模板**：根布局定义 `%s | NKDShinKu`，每个页面只填自己的标题，自动拼出全站统一的形态；
- **描述（description）**：每页手写，直接复用文章的 frontmatter 摘要——这段文字会出现在搜索结果的摘要行里，写得好坏直接影响点击；
- **canonical（规范链接）**：每个页面显式声明自己的权威 URL。静态站常见的重复内容问题（带不带尾斜杠、分页参数）靠它收口；
- **分页页 noindex**：`/posts/page/2/` 这类分页路由显式标记 `robots: { index: false }`——它们是导航辅助，不该和正文页抢收录。

有一个流传很广的误解顺手澄清：`<meta name="keywords">` 早在十多年前就被 Google 无视了，堆关键词没有任何排名收益。我的 frontmatter 里保留了这个字段，纯粹是「写了无害」的冗余——真正的关键词工作发生在标题、描述和正文里。

## sitemap 与 robots：给爬虫画地图

**sitemap.xml** 是你主动递给搜索引擎的「全站页面清单」。我的实现是一个 Next.js 的 metadata route（构建期生成静态文件）：

- 首页与板块页高优先级，文章页次之，分类标签页再次之；
- 文章条目带上 `lastModified`（取 frontmatter 的更新时间），爬虫据此判断「这篇有没有新变化」；
- 分页页不进 sitemap（与 noindex 呼应）。

诚实说明：Google 官方已确认基本忽略 sitemap 里的 `priority` 和 `changefreq` 字段——真正被消费的是**这份清单本身**（哪些 URL 存在、何时更新过）。所以别在优先级数值上纠结，保证「全、新、准」三个字就够了。

**robots.txt** 则简单到只有四行：允许所有爬虫、声明 sitemap 地址。它的作用不是「SEO 加分项」，而是防止未来的你误加规则把整站挡在外面——保持极简就是最好的实践。

最后，提交动作要做：sitemap 写好了要主动送到搜索引擎面前（Google Search Console 里提交一次即可），否则爬虫发现你的速度取决于外链的多寡。

## 结构化数据：让机器「看懂」内容

元信息告诉爬虫「这个页面叫什么」，结构化数据则告诉它「这个页面**是什么类型的东西**」。实现方式是在页面里嵌入一段 JSON-LD：

```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "文章标题",
  "datePublished": "2026-09-10",
  "dateModified": "2026-09-10",
  "author": { "@type": "Person", "name": "NKDShinKu" },
  "keywords": ["giscus", "静态博客"]
}
```

我的每篇文章详情页都注入了这段 BlogPosting 结构化数据，字段直接从 frontmatter 派生（发布时间、更新时间、作者、关键词），构建期生成，零维护。

需要注意结构化数据的边界：它不是万能加分项。Google 在 2026 年 5 月全面退役了 FAQ 富结果——结构化数据的具体形态会随政策起落，**长期值得投资的只有内容主体类标记**（Article、Person、Organization 这类描述「这是什么」的基础词汇）。别为了某种富结果样式过度堆砌 schema。

## 社交分享卡：OG 与 Twitter Card

把博客链接粘贴到 Telegram、Discord 或推特里时出现的「图片 + 标题 + 摘要」卡片，读的是 **Open Graph 协议**标签——Facebook 在 2010 年推出的这套约定，如今是几乎所有社交平台的事实标准：

- `og:image`：卡片配图，推荐 1200×630。我给全站配了一张静态品牌图（和站点同风格的极光 + logo + 站名），文章页与首页共用；
- `og:title` / `og:description`：卡片文案，与页面元信息同源；
- `twitter:card: summary_large_image`：推特自己的协议标签，声明用大图卡片渲染。

对技术博客来说，这张卡是**点击率的第一战场**——读者在群里看到你的链接，卡片质感几乎等于第一印象。顺便一提微信的特例：它基本不读 OG 标签，国内分享生态自成体系，不必为它优化。

## 图标集与 manifest：站点身份的一致性

favicon 对排名没有直接影响，但它是「品牌一致性」的一部分：浏览器标签页、iOS 添加到主屏幕、Android 安装 PWA，每个场景对图标尺寸的要求都不同。我的做法是用脚本从一份 SVG 源文件派生出全套——`favicon.ico`（16/32/48）、`apple-touch-icon`（180）、PWA 的 192/512 图标，外加一个声明主题色的 `manifest.webmanifest`。

这套东西做好了是一次性工程：换 logo 时改一个 SVG 重跑脚本，全平台图标同步更新。

## 性能即 SEO：Core Web Vitals

页面体验是 Google 的正式排名信号，度量衡是 Core Web Vitals 三指标：

- **LCP**（最大内容绘制）：主内容多快出现，目标 2.5 秒内；
- **CLS**（累积布局偏移）：页面会不会跳来跳去，目标接近 0；
- **INP**（交互到下一次绘制）：点击后响应多快（2024 年 3 月起取代了原来的 FID），目标 200ms 内。

静态导出的架构在这三件事上是躺赢的：HTML 直出、无客户端渲染等待、图片全部显式宽高加懒加载（CLS 天然为 0）。我用 Lighthouse 对四个核心页面跑了两轮全量审计，桌面端性能分 97–100、移动端 80–93、全站 CLS 为 0——这些数字本身就是静态架构的红利。移动端分数还有优化空间（主要是外部图片与第三方脚本），这是下一步的功课，但地基已经是现成的。

## RSS：SEO 之外的分发通道

严格说 RSS 不属于 SEO——它不参与搜索排名。但它是内容分发的另一条腿：读者用阅读器订阅，新文章自动送达，不依赖任何算法推荐。实现上是一个构建期生成的 RSS 2.0 路由，全量文章、摘要取自 frontmatter。

在 AI 阅读器与独立博客回潮的当下，RSS 的价值反而在回升。对个人博客来说，它是「不讨好算法、直接触达订阅者」的唯一通道。

## AI 时代的 SEO：llms.txt

最新的一条基建是给 AI 看的。2024 年社区提出了 `llms.txt` 约定：在站点根目录放一份 Markdown 文件，写清站点是什么、有哪些板块、每篇文章的标题与链接——相当于递给大模型一份「站点说明书」，让 AI 在引用你的内容时理解更准确。

诚实评估：这是**尚无搜索引擎官方采用的前瞻约定**，收益是赌「AI 搜索成为流量入口」的未来。但实现成本几乎为零——我的实现是一个构建期生成的 route handler，自动汇总全站文章清单，发新文自动更新，零维护。

比起文件本身，更值得做的 AI 时代准备其实是：**内容结构清晰、事实表述准确、观点可独立引用**——大模型抓取网页时，最容易被引用的正是那种「自包含、有结论、有上下文」的段落。

## 一份可以直接抄的自查清单

把上面所有内容压成一张表，逐项打勾，你的静态博客 SEO 地基就齐了：

- [ ] 每页独立的 title 与 description，全站统一标题模板
- [ ] 每页声明 canonical 规范链接；导航性质的页面（分页等）noindex
- [ ] sitemap.xml 覆盖全部应收录页面，并提交到 Google Search Console
- [ ] robots.txt 保持极简，声明 sitemap 地址
- [ ] 文章页注入 Article/BlogPosting 结构化数据
- [ ] Open Graph 标签 + 一张 1200×630 分享图 + twitter card
- [ ] favicon 全套（ico / apple-touch / PWA 图标）+ manifest
- [ ] Core Web Vitals 达标（LCP < 2.5s / CLS ≈ 0 / INP < 200ms）
- [ ] RSS 订阅入口
- [ ] （前瞻）llms.txt

## 结语

技术 SEO 是一份「做一次、长期吃红利」的基建：它不会让你的烂文章排到第一，但能保证你的好文章不被埋没。对静态博客来说，这套基建的成本低到不成比例——一个配置文件、一个构建脚本、一张分享图，换来的是爬虫、平台和 AI 三条分发通道全部畅通。
